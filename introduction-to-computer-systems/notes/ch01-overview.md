## 1.1 冯·诺依曼结构

<a id="sec1-1-1"></a>
### 1.1.1 冯·诺依曼结构基本思想 ★★★

#### 📌 考点概括

考查**存储程序**概念与**五大部件**识别。常以"冯·诺依曼结构最核心的思想是什么"出题。

#### 📖 详细讲解

**存储程序（Stored Program）**——冯·诺依曼结构的灵魂：**程序和数据以同等地位存放在存储器中，按地址访问、顺序执行。** 之前程序靠插拔导线"输入"；冯·诺依曼的洞见是把程序本身也当数据存进内存，计算机自动逐条取指执行。

**五大部件：**

| 部件 | 英文 | 核心职责 |
|------|------|----------|
| **运算器** | ALU | 算术运算和逻辑运算 |
| **控制器** | CU | 指挥各部件协同，控制指令执行顺序 |
| **存储器** | Memory | 存放程序和数据（注：冯氏定义中特指**内存/主存**） |
| **输入设备** | Input | 将外部信息送入计算机 |
| **输出设备** | Output | 将计算结果送出计算机 |

> **要点**：CPU = 运算器 + 控制器（不是单独的五大部件之一）；硬盘属于I/O设备，不是存储器。

#### 🔍 举例推演

计算 `3+5` 的部件协作：触摸屏(输入)→3和5从硬盘加载到内存→控制器取指"加法"→ALU执行得8→结果写回内存→屏幕显示(输出)。

#### ✏️ 真题训练

**题1（单选）** 冯·诺依曼计算机中，程序和数据以（ ）存放在存储器。

A. 二进制  B. 十进制  C. 八进制  D. ASCII码

> **答案：A**。二进制统一表示一切（指令和数据），是存储程序概念的基础。

---

**题2（简答）** 简述"存储程序"概念的核心思想及意义。

> **答案**：核心思想——①程序和数据以同等地位存储在内存中，均二进制编码；②计算机按地址逐条取指，自动顺序执行。意义——使计算机成为**通用**工具（换程序只需改内存，不需改硬件），奠定软件产业基础。

<a id="sec1-1-2"></a>
### 1.1.2 冯·诺依曼机基本结构 ★★★

#### 📌 考点概括

考查五大部件的**互联方式**和**数据通路**。常以"数据流/控制流经过哪些部件"出题。

#### 📖 详细讲解

**数据流 vs 控制流：**

| 类型 | 含义 | 典型路径 |
|------|------|----------|
| **数据流** | 数据的传输 | 输入设备→存储器；存储器↔运算器；存储器→输出设备 |
| **控制流** | 控制信号 | 控制器→所有其他部件（单向发出） |

> 控制器只发控制信号不处理数据；运算器既接收控制信号又处理数据。

现代计算机采用**总线**互联，分为三类：**数据总线**（双向）、**地址总线**（单向，CPU发出）、**控制总线**（各线方向固定）。

#### 🔍 举例推演

执行"从地址X取数，加1后存回地址Y"：
- 取指：PC→地址总线，读命令→控制总线，指令→控制器
- 执行：控制器发地址X+读信号→数据→ALU；控制器发"加1"操作码→ALU运算；结果+地址Y+写信号→写回存储器

#### ✏️ 真题训练

**题3（单选）** 指令从存储器取到控制器属于（ ）。

A. 数据流  B. 控制流  C. 两者都是  D. 两者都不是

> **答案：A**。指令本身作为数据在总线上传输属于数据流；控制流特指控制器**发出**的信号。

<a id="sec1-1-3"></a>
### 1.1.3 程序和指令的执行过程 ★★★

#### 📌 考点概括

考查**取指→译码→执行**循环及**PC（程序计数器）**的作用。

#### 📖 详细讲解

**指令周期三步：**

| 阶段 | 操作 | PC行为 |
|------|------|--------|
| **取指 (Fetch)** | 按PC从内存读指令→指令寄存器IR | PC自动+1 |
| **译码 (Decode)** | 解析IR：操作码 + 操作数地址 | 不变 |
| **执行 (Execute)** | ALU运算/访存/跳转 | 顺序指令不变；跳转指令→PC改为目标地址 |

> **PC核心作用**：始终存放下一条指令的地址。类比"书签"——指向要执行的下一行。跳转指令=CALL/RET指令会修改PC（详见第3章[过程调用的机器级表示](./ch03-machine-level.md#sec3-4-1)）。

#### 🔍 举例推演

三条指令：`LOAD R1,[200]`(100号)→`ADD R1,#5`(101号)→`STORE R1,[300]`(102号)，初始PC=100。

| 步骤 | PC变化 | 操作 |
|------|--------|------|
| 取指1 | 100→101 | 取"LOAD R1,[200]"→IR |
| 执行1 | 101 | [200]→R1 |
| 取指2 | 101→102 | 取"ADD R1,#5"→IR |
| 执行2 | 102 | R1=R1+5 |
| 取指3 | 102→103 | 取"STORE R1,[300]"→IR |
| 执行3 | 103 | R1→[300] |

若有`JMP 105`则在执行阶段PC设为105。

#### ✏️ 真题训练

**题4（单选）** PC的位数取决于（ ）。

A. 指令字长  B. 机器字长  C. 存储器容量  D. 数据总线宽度

> **答案：C**。PC存放地址，位数须覆盖整个地址空间。4GB内存按字节编址需32位PC。

---

**题5（简答）** 简述取指阶段PC的行为规律。

> **答案**：取指阶段PC必+1（或+当前指令长度）；执行阶段仅**控制转移类指令**（跳转/调用/返回）会修改PC。

## 1.2 程序开发与执行

<a id="sec1-2-1"></a>
### 1.2.1 程序设计语言和翻译程序 ★★

#### 📌 考点概括

考查**三级语言**区别及**翻译程序与解释程序**对比。常以匹配题/选择题出现。

#### 📖 详细讲解

**三级语言：**

| 级别 | 语言 | 示例 | 特点 |
|------|------|------|------|
| 低级 | 机器语言 | `10110000 01100001` | 二进制，唯一硬件直接理解，平台相关 |
| 中低级 | 汇编语言 | `MOV AL, 61h` | 助记符，与机器指令**一一对应** |
| 高级 | 高级语言 | `x = 97;` | 接近人类语言，平台无关 |

**翻译程序 vs 解释程序：**

| | 翻译程序（编译器） | 解释程序（解释器） |
|------|-------------------|---------------------|
| 机制 | 一次性翻译整个源程序 | 逐句翻译并执行 |
| 产物 | 生成独立可执行文件 | 不生成独立文件 |
| 速度 | 快 | 慢 |
| 典型 | gcc, clang | Python解释器, Bash |

> Java采用混合模式：javac编译为字节码→JVM解释执行（带JIT编译）。

#### 🔍 举例推演

C语句 `y = a * b + c;` 在各层的表示：
- **C**: 1行
- **x86汇编**: 4条(`mov; imul; add; mov`) 
- **x86机器码**: 4条指令（一一对应）

#### ✏️ 真题训练

**题6（单选）** 以下关于汇编语言的描述正确的是（ ）。

A. 可直接运行  B. 一条对应多条机器指令  C. 可读性比高级语言好  D. 与机器语言一一对应

> **答案：D**。

---

**题7（简答）** 简述翻译程序与解释程序的区别。

> **答案**：翻译程序一次性翻译整个源程序→独立可执行文件→执行快（如gcc）；解释程序逐句翻译逐句执行→不生成独立文件→执行慢但调试方便（如Python）。

<a id="sec1-2-2"></a>
### 1.2.2 从源程序到可执行文件 ★★★

#### 📌 考点概括

**本章最重要考点之一。** 考查**预处理→编译→汇编→链接**四阶段的输入输出和职责。必有简答题。

#### 📖 详细讲解

```
hello.c ──预处理──→ hello.i ──编译──→ hello.s ──汇编──→ hello.o ──链接──→ hello
 源程序      (cpp)    预处理后    (ccl)   汇编程序    (as)   可重定位   (ld)   可执行文件
                       源程序                      目标文件
```

| 阶段 | 输入 | 输出 | 程序 | 核心工作 |
|------|------|------|------|----------|
| **预处理** | `.c` | `.i` | cpp | 宏展开、头文件包含(#include)、条件编译、删除注释 |
| **编译** | `.i` | `.s` | ccl | 词法分析→语法分析→语义分析→优化→**生成汇编代码** |
| **汇编** | `.s` | `.o` | as | 汇编指令→**机器指令**（二进制），生成可重定位目标文件 |
| **链接** | `.o`+库 | 可执行 | ld | 符号解析+重定位，合并目标文件和库，确定最终地址 |

**关键辨析**：
- 编译产生汇编代码（文本，人类可读），汇编产生机器代码（二进制）。它们是两个独立阶段。
- `.o`文件已是机器指令，但地址是"浮动"的（相对地址），链接后地址才被"钉死"。
- 头文件只在预处理阶段起作用（原样插入源文件），不参与编译、汇编、链接。

> **类比**：写书→出版——预处理=插入参考文献内容，编译=中译英草稿，汇编=排版为印刷版面，链接=装订成书建立页码索引。

#### 🔍 举例推演

`hello.c` 四阶段变化：

```c
// hello.c
#include <stdio.h>
#define MSG "Hello\n"
int main() { printf(MSG); return 0; }
```

1. **预处理后**：stdio.h全部内容插入，MSG展开为`"Hello\n"`
2. **编译后**：生成x86-64汇编代码（`.string "Hello"`、`call puts`等）
3. **汇编后**：二进制`.o`文件，`call puts`地址未定（用`objdump -d`可反汇编查看）
4. **链接后**：可执行文件，所有地址已确定

#### ✏️ 真题训练

**题8（排序）** 将四阶段按正确顺序排列：预处理、链接、汇编、编译，并写出各阶段的输入输出文件类型。

> **答案**：**预处理(.c→.i) → 编译(.i→.s) → 汇编(.s→.o) → 链接(.o+库→可执行)** 。记法：P-C-A-L。

---

**题9（简答）** 什么是链接？链接器完成哪两项主要工作？

> **答案**：链接将多个`.o`文件及库合并为可执行文件。两项工作：①**符号解析**——建立未定义符号（如外部函数）与其定义的关联；②**重定位**——将相对地址转换为最终绝对地址。详见[第4章链接](./ch04-linking.md#sec4-1-1)。

<a id="sec1-2-3"></a>
### 1.2.3 可执行文件的启动和执行 ★★

#### 📌 考点概括

考查OS**加载器**的角色、**程序入口点**概念及PC初始化过程。

#### 📖 详细讲解

可执行文件"活起来"靠OS加载器（Loader）：

```
Shell输入 ./hello
  → fork() 创建子进程
  → execve("./hello", ...) 
  → 加载器: ①读ELF头→获取入口地址（ELF格式详见[第4章ELF文件格式](./ch04-linking.md#sec4-2-1)）
            ②创建虚拟地址空间
            ③映射代码段(.text)和数据段(.data)
            ④加载动态链接器(如需)
            ⑤设置栈、堆
            ⑥PC = 入口地址(_start)
  → CPU从入口开始执行
```

**关键概念：**

| 概念 | 说明 |
|------|------|
| **程序入口** | 第一条指令地址，是`_start`（crt0提供），**不是**`main` |
| **_start流程** | `_start`→初始化C环境(栈/argc/argv)→调用`main`→`main`返回→`exit` |
| **PC初始化** | OS将PC设为入口地址 |
| **fork+execve** | Unix启动程序标准模式：fork创建进程壳→execve填入程序内容 |

#### 🔍 举例推演

`./hello` 执行链：Shell→fork→execve读取ELF头(入口=0x401000)→建立地址空间→mmap代码段/数据段→PC=0x401000→_start→__libc_start_main→main→printf→exit→进程结束→Shell收回控制权。

#### ✏️ 真题训练

**题10（单选）** 可执行文件的Entry Point指向（ ）。

A. main函数  B. _start  C. 动态链接库入口  D. Shell代码

> **答案：B**。`main`之前C运行时初始化代码`_start`已运行。

## 1.3 计算机系统抽象层

<a id="sec1-3-1"></a>
### 1.3.1 计算机系统抽象层的转换 ★★★

#### 📌 考点概括

考查**七层抽象模型**各层名称、功能和提供的接口。

#### 📖 详细讲解

计算机系统的七层抽象（自底向上）：

```
⑦ 应用层（Application）        接口：用户界面
⑥ 高级语言层（High-Level Lang） 接口：编程语言语法
⑤ 操作系统层（OS）             接口：系统调用
④ 指令集架构层（ISA）  ←⭐    接口：指令集+寄存器模型（软硬件分界线！）
③ 微体系结构层（Microarch）     接口：(内部，对外透明)
② 数字逻辑层（Digital Logic）   接口：(内部)
① 物理层（Physical/Device）     接口：(内部)
```

**各层核心问题：**

| 层 | 核心问题 | 本课程对应 |
|----|---------|-----------|
| 物理层 | 怎样制造可靠开关？ | 不涉及 |
| 数字逻辑层 | 怎样用开关搭加法器？ | 不涉及 |
| 微体系结构层 | 怎样设计高性能CPU内部？ | 不涉及 |
| **ISA层** | **指令是什么格式？** | 第3章核心 |
| 操作系统层 | 怎样安全多任务？ | 第8章 |
| 高级语言层 | 怎样写出高效代码？ | 贯穿各章 |
| 应用层 | 怎样满足用户需求？ | 不涉及 |

> **类比**：邮政分层——你写信(应用层)用中文(语言层)→邮局投递(OS层)→信封格式规定(ISA)→内部分拣机(微架构)→电路(数字逻辑)→晶体管(物理)。你只需写好信封(遵守接口)，不必知道分拣机如何工作。

#### 🔍 举例推演

浏览器点击链接→各层反应：应用层(检测点击)→高级语言层(调用fetch)→OS层(socket/connect/send系统调用)→ISA层(syscall指令)→微架构(流水线执行)→数字逻辑(ALU计算)→物理(晶体管开关)。

#### ✏️ 真题训练

**题11（填空）** 七层抽象中软硬件分界线是\_\_\_\_\_\_层，向上提供的抽象是\_\_\_\_\_\_。

> **答案：指令集架构（ISA）；指令集（和寄存器模型）**。

---

**题12（简答）** 解释计算机系统中"透明"的含义并举例。

> **答案**：透明=某一层的细节对另一层**不可见/无需关心**。例：微体系结构对高级语言程序员透明——无论CPU内部是几级流水线，程序结果都不受影响。注意：计算机科学中"透明"与日常语义相反。

---

<a id="sec1-3-2"></a>
### 1.3.2 计算机系统核心层之间的关联 ★★★

#### 📌 考点概括

考查**ISA的关键地位**（软硬件接口）及各层透明性关系。

#### 📖 详细讲解

**ISA：软硬件之间的契约**

ISA定义了什么？指令集、寄存器组、寻址方式、数据类型、内存模型、异常处理机制。它是软件唯一"看见"的硬件接口。

> **类比**——ISA是插座国标：电器厂商(软件)按国标做插头，插座厂商(硬件)按国标做插座，互不依赖内部实现。Intel和AMD的CPU内部迥异，但因遵守x86 ISA，都能运行Windows。

**透明性关系：**

| "谁"对"谁"透明 | 含义 |
|---------------|------|
| 微体系结构对ISA | 不同CPU内部实现不同，指令集相同 |
| ISA对高级语言 | C程序不关心底层用ADD还是LEA |

关于ISA与上下层关联详见[第3章ISA讲解](./ch03-machine-level.md#sec3-1-2)。

#### ✏️ 真题训练

**题13（简答）** 为什么说ISA是计算机系统中最关键的抽象层？

> **答案**：ISA是软硬件之间的正式契约——软件只需面向ISA编译，硬件只需正确实现ISA即可。同ISA保障二进制兼容（软件生态），不同微架构允许硬件差异化竞争。详见[第3章ISA](./ch03-machine-level.md#sec3-1-2)。

<a id="sec1-3-3"></a>
### 1.3.3 计算机系统的不同用户 ★☆

#### 📌 考点概括

考查四类用户的**关注点差异**。常以场景判断题出题。

#### 📖 详细讲解

| 用户类型 | 所在层 | 关注的问题 | 是否需了解底层 |
|----------|--------|-----------|---------------|
| **最终用户** | 应用层 | "软件好用吗？快不快？" | 不需要 |
| **系统管理员** | OS层 | "服务器宕机没？磁盘够吗？" | 需要理解OS机制 |
| **应用程序员** | 高级语言层 | "怎样用Python高效处理数据？" | 部分了解(优化时) |
| **系统程序员** | ISA+OS层 | "如何设计编译器/OS内核？" | 必须精通 |

> **类比**：最终用户=驾驶员(关心方向盘)→应用程序员=汽车设计师(关心外观功能)→系统程序员=发动机工程师(关心内部原理)→系统管理员=车队调度(关心维护调度)。

#### 🔍 举例推演

面对"程序运行慢"：
- 最终用户："换台新电脑"
- 管理员："是否有其他进程抢占CPU？I/O瓶颈？"
- 应用程序员："算法是不是O(n^2)？换哈希表优化"
- 系统程序员："检查汇编代码，是否有不必要的访存？缓存miss？"

#### ✏️ 真题训练

## 1.4 计算机性能评估

<a id="sec1-4-1"></a>
### 1.4.1 计算机性能的定义 ★★

#### 📌 考点概括

考查**响应时间 vs 吞吐率**的区别，**CPU时间 = 用户CPU时间 + 系统CPU时间**。

#### 📖 详细讲解

| 维度 | 定义 | 度量 | 类比 |
|------|------|------|------|
| **响应时间** | 任务开始到完成的时间 | 秒、ms | 单人过安检耗时 |
| **吞吐率** | 单位时间完成的任务数 | 任务/秒、MB/s | 安检口每小时通过人数 |

两者常矛盾（为提吞吐率可能牺牲单个请求的响应时间）。

**CPU时间的组成：**

```
墙上时钟时间 = CPU时间 + I/O等待 + 其他进程占用
CPU时间 = 用户CPU时间(执行用户程序指令) + 系统CPU时间(执行系统调用在内核的开销)
```

**时钟周期**：CPU内部恒定频率的"节拍"——时钟信号。T(周期) = 1/f(主频)。f=3GHz→T≈0.33ns。详见第3章[ISA与时钟](./ch03-machine-level.md#sec3-1-2)。

#### 🔍 举例推演

Web服务器处理请求分析（总200ms延迟）：CPU时间10ms(用户7ms+系统3ms)+磁盘I/O等待50ms+网络140ms。优先优化网络（占比70%）而非CPU。

#### ✏️ 真题训练

**题15（单选）** 以下哪个衡量吞吐率？（ ）

A. 打开Word需3秒  B. 数据库每秒处理1000查询  C. 按键到显示延迟  D. 网页加载需2秒

> **答案：B**。"每秒1000查询"是单位时间工作量，属吞吐率。

<a id="sec1-4-2"></a>
### 1.4.2 计算机性能的测试 ★★

#### 📌 考点概括

考查**时钟周期/主频/CPI/MIPS/MFLOPS**的定义及关系。MIPS不能跨ISA比较是常见陷阱。

#### 📖 详细讲解

| 指标 | 定义 | 公式 | 单位 |
|------|------|------|------|
| 时钟周期(T) | 一个时钟脉冲时间 | T=1/f | s(ns) |
| 主频(f) | 每秒时钟周期数 | f=1/T | Hz(GHz) |
| CPI | 平均每条指令周期数 | CPI=总周期数/指令数 | 无量纲 |
| IPC | 每周期指令数 | IPC=1/CPI | 无量纲 |
| MIPS | 每秒百万条指令 | MIPS=f/(CPI×10^6) | 百万条/s |
| MFLOPS | 每秒百万次浮点运算 | 实测 | 百万次/s |

**MIPS的局限性**：不同ISA指令功能不同（RISC一条指令通常比CISC简单，天然MIPS更高但未必更"快"）；同CPU不同程序MIPS也不同（指令混合不同导致CPI不同）；**MIPS不能跨ISA比较**。

#### 🔍 举例推演

主频2GHz，程序执行10^9条指令，平均CPI=1.5：
- T=1/(2×10^9)=0.5ns
- 执行时间=10^9×1.5×0.5×10^(-9)=0.75秒
- MIPS=2×10^9/(1.5×10^6)≈1333

#### ✏️ 真题训练

**题16（填空）** CPU主频3GHz，T=\_\_\_\_ns；CPI=1.2，MIPS=\_\_\_\_。

> **答案：0.333ns；2500**。T=1/(3×10^9)=0.333ns；MIPS=3×10^9/(1.2×10^6)=2500。

---

**题17（判断）** 计算机A的MIPS=500，B的MIPS=300，因此A一定比B性能好。（ ）

> **答案：错误**。MIPS不能跨平台比较——不同ISA指令含金量不同，且同ISA不同程序MIPS也会变化。正确方法是用**执行时间**比较。

<a id="sec1-4-3"></a>
### 1.4.3 用指令执行速度进行性能评估 ★★★

#### 📌 考点概括

考查**CPU执行时间公式推导**和**Amdahl定律计算**。本章唯一可能出现计算题的考点。

#### 📖 详细讲解

**核心公式：**

> **T_cpu = IC × CPI × T = IC × CPI / f**

- **IC**（Instruction Count）：程序执行的指令总数——由**编译器**和**ISA**决定
- **CPI**（Cycles Per Instruction）：平均每条指令时钟周期——由**微体系结构**决定
- **T / f**（时钟周期/主频）——由**半导体工艺**和**电路设计**决定

**Amdahl定律：**

> **Speedup = 1 / [(1 - f) + f/S]**

- **f** = 可改进部分占总时间比例 (0<f≤1)
- **S** = 可改进部分的加速比 (S>1)
- 推论：整体加速**上限** = 1/(1-f)（即使S→∞也无法突破）

**核心洞察**：要获得显著整体提升必须关注**占比大的部分**——这是Amdahl定律最重要的工程启示。

| f=50%, S=∞ | Speedup=1/0.5=2 | 优化50%的部分无限加速，仅整体提速2倍 |
| f=90%, S=∞ | Speedup=1/0.1=10 | 优化90%的部分无限加速，整体提速10倍 |
| f=99%, S=∞ | Speedup=1/0.01=100 | 优化99%才能提速100倍 |

> **类比**：CPU时间=搬完一堆砖的时间=砖块数(IC)×每块耗时(CPI)×每步时间(T)。减少IC=换大铲子(CISC)；降CPI=练肌肉(流水线)；缩T=喝红牛(提频)。

#### 🔍 举例推演

**例1（CPU时间计算）**：程序在CPU X(2.5GHz)运行需10秒。设计CPU Y，主频3.0GHz，但CPI增20%。问：Y需减少多少指令才能运行P仅6秒？

解：设CPI_X=C，CPI_Y=1.2C。
- T_X=IC_X×C/2.5=10
- T_Y=IC_Y×1.2C/3.0=6
- 两者相除：(IC_Y/IC_X)×1.2×(2.5/3.0)=0.6 → IC_Y/IC_X=0.6 → 需减少40%。

**例2（Amdahl定律）**：程序80%时间浮点运算(加速4倍)，20%整数运算(不加速)。求整体加速比。

解：f=0.8, S=4 → Speedup=1/[(1-0.8)+0.8/4]=1/[0.2+0.2]=2.5倍。

**追问**：若想整体加速5倍，浮点需加速到多少？

解：5=1/[0.2+0.8/S] → 0.2+0.8/S=0.2 → 0.8/S=0 → S→∞，不可能！因上限=1/0.2=5，需无限加速才能逼近。

#### ✏️ 真题训练

**题18（单选）** 某程序200秒中150秒用于浮点运算。将浮点加速5倍后程序运行时间变为（ ）。

A. 40秒  B. 70秒  C. 80秒  D. 120秒

> **答案：C**。f=150/200=0.75, S=5, Speedup=1/[(1-0.75)+0.75/5]=1/0.4=2.5, 新时间=200/2.5=80秒。或直接：整数50秒+浮点30秒=80秒。

**题19（计算）** CPU主频1GHz，指令分布如下。求(1)平均CPI；(2)MIPS；(3)若指令总数2×10^8，求CPU执行时间。

| 指令类型 | 占比 | CPI |
|----------|------|-----|
| 整数ALU | 50% | 1 |
| 访存 | 30% | 3 |
| 分支 | 15% | 2 |
| 浮点 | 5% | 5 |

> **答案**：
> (1) CPI_avg=0.50×1+0.30×3+0.15×2+0.05×5=0.50+0.90+0.30+0.25=**1.95**
> (2) MIPS=10^9/(1.95×10^6)≈**512.8**
> (3) T=2×10^8×1.95/10^9=**0.39秒**

**题20（计算）** 某程序A(30%)、B(50%)、C(20%)三个阶段的CPU时间占比。三个优化方案：
- 方案1：A加速10倍
- 方案2：B加速3倍
- 方案3：C加速100倍

通过计算说明哪个方案整体加速效果最好。

> **答案**：
> 方案1：f=0.3,S=10 → Speedup=1/[(1-0.3)+0.3/10]=1/0.73≈**1.37**
> 方案2：f=0.5,S=3 → Speedup=1/[(1-0.5)+0.5/3]=1/0.667≈**1.50**
> 方案3：f=0.2,S=100 → Speedup=1/[(1-0.2)+0.2/100]=1/0.802≈**1.25**
>
> **方案2最优**。虽然A、C加速比更高，但B占比最大(50%)，中等加速乘大占比整体收益最高——验证Amdahl定律核心：**优先优化占比大的部分**。
